Understanding each component of the dynamic model

From the inertia matrix to gravity terms — read the RV-M1's torques and you read its physics.

Lecturer. bibliosense Lecture. 04
By now you've run five_dof_dynamics.m and watched the numbers fly past — D, h, c, all assembled in a single line. Today we slow that line down. We open up the inertia matrix and ask why it changes so much when the arm extends. We chase the Coriolis and centrifugal terms until you can predict, before pressing run, when they'll matter and when they won't. And we look at gravity not as a nuisance but as the thing your controller most wants to know about. By the end you should read the RV-M1's torque vector the way a clinician reads a heartbeat.

0What this lecture covers

This module takes the dynamic equation $\boldsymbol\tau = \mathbf{D}(\mathbf{q})\ddot{\mathbf{q}} + \mathbf{h}(\mathbf{q},\dot{\mathbf{q}}) + \mathbf{c}(\mathbf{q})$ apart, term by term, using the 5-DOF Mitsubishi RV-M1 as our running example.

We'll connect each mathematical object back to the MATLAB code you already wrote — five_dof_dynamics.m — so the symbols stop being abstract and start being something you can poke at numerically. Then we'll layer that understanding into a working PD + gravity-compensation controller and see how component-level insight changes control design.

If you can predict the sign and rough magnitude of each term before MATLAB returns it, you understand the dynamics. That's the bar.
What you'll be able to do. Read individual entries of $\mathbf{D}(\mathbf{q})$ as physical couplings, predict when $\mathbf{h}$ matters, and write a gravity-compensated controller that actually works.

1The inertia matrix $\mathbf{D}(\mathbf{q})$ — configuration-dependent mass

The inertia matrix is a $5\times 5$ symmetric, positive-definite map from joint accelerations to joint torques. In five_dof_dynamics.m it appears as elements like D(1,1) and D(1,2), built from the $U$ matrices and link inertia tensors $J_i$ via $D_{ij} = \sum_k \text{tr}(U_{ki} J_k U_{kj}^\top)$.

Diagonal entries are self-inertias — how much torque joint $i$ needs to accelerate itself, given everything riding on it. Off-diagonal entries are coupling inertias — when joint $i$ accelerates, it shoves joint $j$.

For the RV-M1 specifically: $D_{11}$ collects all five links rotating about the base. $D_{22}$ varies dramatically as the 250 mm upper arm extends or retracts. $D_{23}$ is strong because the 160 mm forearm sits across both joints.

The inertia matrix is the robot's configuration-aware mass. There is no single number — only a matrix that changes with every pose.
Diagonal vs off-diagonal. Diagonals tell you how heavy each joint feels. Off-diagonals tell you how much joint $i$ pushes joint $j$ when it accelerates. Both change with $\mathbf{q}$.
Properties guaranteed by the formulation. The $\text{tr}(UJU^\top)$ structure automatically gives a symmetric, positive-definite $\mathbf{D}$. You don't have to enforce it — the math does.

2Coriolis and centrifugal forces $\mathbf{h}(\mathbf{q},\dot{\mathbf{q}})$

The vector $\mathbf{h}$ collects velocity-dependent forces — phantom torques that vanish at rest and grow quadratically with speed. Two flavours:

  • Centrifugal (terms in $\dot q_i^2$): forces that arise from a single joint's own motion. When joint 1 spins, the 250 mm and 160 mm arms get flung outward.
  • Coriolis (terms in $\dot q_i \dot q_j$, $i\neq j$): forces that arise when two joints move simultaneously. When joints 1 and 2 move together, they create a torque at joint 3.

In five_dof_dynamics.m these appear as the Christoffel symbols h111, h112, ... assembled into the h vector. Because they scale with $\dot{\mathbf{q}}^2$, doubling speed quadruples the torque — which is why high-speed robots can't be controlled with the same gains as slow ones.

At low speed you can almost ignore $\mathbf{h}$. Past a few rad/s, ignoring it is how robots overshoot.
Why velocity terms feel like 'phantom forces'. They don't appear in static analysis and they vanish at $\dot{\mathbf{q}} = 0$. They emerge purely from the changing geometry as the robot moves — a Lagrangian artefact that becomes very real when your tracking error blows up.
Quadratic scaling. Centrifugal $\propto \dot q_i^2$, Coriolis $\propto \dot q_i \dot q_j$. Either way: double the speed, quadruple the force. There is no linear regime.
Centrifugal forces — single joint at varying speeds
% Test centrifugal forces: single joint motion at different speeds
config = [0; 45; 30; 0; 0];  % Fixed configuration
acc = zeros(5,1);

speeds = [0, 1, 2, 5, 10];   % rad/s
for i = 1:length(speeds)
    veloc = [speeds(i); 0; 0; 0; 0];
    torque = five_dof_dynamics(config, veloc, acc, 'deg');
    fprintf('Speed %.1f rad/s: Torque magnitude = %.3f N*m\n', ...
            speeds(i), norm(torque));
end

3When velocity terms matter — the speed thresholds

Knowing $\mathbf{h}$ exists isn't enough; you need to know when it dominates. The percentage of total torque attributable to velocity terms scales roughly with the square of joint speed. For the RV-M1's geometry and typical operating envelope:

  • Below 0.5 rad/s velocity terms are essentially noise — a basic PID will track fine.
  • Between 1 and 3 rad/s they reach 5–15% — gravity compensation is enough.
  • Between 3 and 8 rad/s they hit 15–40% — you need active dynamic compensation.
  • Above 8 rad/s they dominate — you must use the full model in feedforward.

These thresholds are robot-specific. For a longer-armed manipulator they shift down; for a tiny wrist-only mover they shift up.

There's no universal cutoff. There is a cutoff for your robot, in your workspace, with your payload — and the only way to find it is to compute it.
Rule of thumb. If your tracking error scales with the square of commanded speed, you're hitting the velocity-term wall. Time to compensate.

4Gravity $\mathbf{c}(\mathbf{q})$ — the term that pays you back

The gravity vector $\mathbf{c}(\mathbf{q})$ is computed in the cc block of five_dof_dynamics.m. For the RV-M1 it usually dominates the torque budget for joints 1–3 — the ones that have to hold up the extended arm.

The shape of the gravity term is what makes it so useful:

  • It depends only on $\mathbf{q}$, not on $\dot{\mathbf{q}}$ or $\ddot{\mathbf{q}}$.
  • For a vertical-axis joint (like joint 1 of the RV-M1), gravity contribution is essentially zero.
  • For shoulder/elbow joints, the contribution follows a clean $\sin(\theta)$ pattern: maximum when the arm is horizontal, zero when vertical.

Because it's a pure function of position, gravity is the easiest term to compensate — you just call five_dof_dynamics(q, 0, 0, ...) and add it as feedforward. That single line of code typically eliminates more steady-state error than any amount of gain tuning.

Gravity is the most predictable part of the dynamics. That's exactly why we compensate it first — high return, low cost.
Why gravity comp is the cheapest win. It's deterministic, it's a function of $\mathbf{q}$ alone, and you already have the code that computes it. Adding it to your controller is a one-line change with order-of-magnitude impact on positioning error.

5Worked example — PD with gravity compensation

This is the simplest controller that takes dynamics seriously. The structure is:

$\boldsymbol\tau = \mathbf{K}_p (\mathbf{q}_d - \mathbf{q}) + \mathbf{K}_d (\dot{\mathbf{q}}_d - \dot{\mathbf{q}}) + \mathbf{c}(\mathbf{q})$

The PD term handles motion error; the gravity term holds the arm up so the PD term doesn't have to fight gravity at steady state. Without the $\mathbf{c}(\mathbf{q})$ term, you'd see constant droop on joint 2 — proportional gain alone can't eliminate a constant disturbance.

The gravity term is computed by calling five_dof_dynamics with zero velocity and acceleration, which mathematically isolates $\mathbf{c}(\mathbf{q})$ from the full dynamic equation.

This controller is naive about $\mathbf{D}$ and $\mathbf{h}$ but smart about gravity — and for slow positioning tasks, that's already enough.
What 'PD + gravity' buys you. Eliminates steady-state droop, keeps gains tuneable, and runs in real time. It's the default first-pass controller for any new robot.

% PD + gravity compensation for the RV-M1.

    Kp = diag([50, 100, 80, 30, 20]);
end
if nargin < 5
    Kd = diag([5, 10, 8, 3, 2]);
end

pos_error = q_desired - q_current;
vel_error = -qd_current;

tau_gravity = five_dof_dynamics(q_current, zeros(5,1), zeros(5,1), 'rad');

tau_total = tau_pd + tau_gravity;
end

6Extracting $\mathbf{D}(\mathbf{q})$ from the dynamics function

Sometimes you want $\mathbf{D}(\mathbf{q})$ on its own — for forward dynamics simulation, for stability analysis, for inverse-dynamics control. five_dof_dynamics.m doesn't expose it directly, but you can recover it column by column with a clever trick.

Given $\boldsymbol\tau = \mathbf{D}(\mathbf{q})\ddot{\mathbf{q}} + \mathbf{h}(\mathbf{q},\dot{\mathbf{q}}) + \mathbf{c}(\mathbf{q})$, set $\dot{\mathbf{q}} = 0$ and $\ddot{\mathbf{q}} = \mathbf{e}_j$ (unit vector at joint $j$). Then $\mathbf{h} = 0$, and $\boldsymbol\tau - \mathbf{c}(\mathbf{q}) = \mathbf{D}\mathbf{e}_j$ — which is exactly the $j$-th column of $\mathbf{D}$. Repeat for $j=1,\dots,5$ and you have the whole matrix.

Five calls give you the inertia matrix without ever opening the function body. That's the elegance of the dynamic equation's linearity in $\ddot{\mathbf{q}}$.
Why this works. $\mathbf{D}$ multiplies $\ddot{\mathbf{q}}$ linearly, so unit accelerations expose its columns. The other terms are killed by setting $\dot{\mathbf{q}}=0$ and subtracting the gravity baseline.
Recover D(q) one column at a time
function D = get_inertia_matrix_fd(q)
% Returns 5x5 inertia matrix D(q) by calling five_dof_dynamics with
% unit accelerations.
n = length(q);
D = zeros(n,n);

for j = 1:n
    qd  = zeros(n,1);
    qdd = zeros(n,1);
    qdd(j) = 1;

    tau   = five_dof_dynamics(q, qd, qdd, 'rad');
    tau_0 = five_dof_dynamics(q, zeros(n,1), zeros(n,1), 'rad');
    D(:,j) = tau - tau_0;
end
end

7Worked example — closed-loop step response on joint 2

Putting it all together: a 5-second simulation of joint 2 stepping to 45° under PD + gravity compensation. The loop computes the control torque, uses get_inertia_matrix_fd to invert $\mathbf{D}$, integrates the resulting acceleration with explicit Euler, and logs everything for plotting.

This is forward dynamics in its rawest form — given a torque, what does the robot actually do? The answer comes from $\ddot{\mathbf{q}} = \mathbf{D}^{-1}(\boldsymbol\tau - \mathbf{h} - \mathbf{c})$, integrated forward in time. You'll see joint 2 settle to 45° with the residual error eliminated by the gravity feedforward.

This is the moment the math becomes a robot. Watch the velocity rise, the acceleration spike, the torque saturate, the position settle.
Why we subtract tau_g inside the integration. The control torque already includes gravity compensation, so when we solve $\mathbf{D}\ddot{\mathbf{q}} = \boldsymbol\tau - \mathbf{c}$, we subtract $\mathbf{c}$ once — not twice.
Tuning gains for joint 2. From the script: $K_p = 60$, $K_d = 10$ are the optimal gains. Higher Kp gives faster rise but oscillation; lower Kp gives sluggish response.
Closed-loop simulation: joint 2 step to 45°
clear; clc;

dt = 0.01;
T = 5;
t = 0:dt:T;
n_joints = 5;

q  = zeros(n_joints, 1);
qd = zeros(n_joints, 1);

q_history   = zeros(n_joints, length(t));
qd_history  = zeros(n_joints, length(t));
tau_history = zeros(n_joints, length(t));

q_desired = zeros(n_joints, 1);
q_desired(2) = deg2rad(45);

Kp = diag([0, 6, 0, 0, 0]);   % optimal: 60 for q2
Kd = diag([0, 1, 0, 0, 0]);   % optimal: 10 for q2

for k = 1:length(t)
    pos_error = q_desired - q;
    vel_error = -qd;
    tau_pd = Kp * pos_error + Kd * vel_error;

    tau_g = five_dof_dynamics(q, zeros(n_joints,1), zeros(n_joints,1), 'rad');
    tau   = tau_pd + tau_g;

    D = get_inertia_matrix_fd(q);
    qdd = D \ (tau - tau_g);

    qd = qd + qdd * dt;
    q  = q  + qd  * dt;

    q_history(:, k)   = q;
    qd_history(:, k)  = qd;
    tau_history(:, k) = tau;
end

8Decomposing torque into gravity, inertial, and velocity contributions

Once you have five_dof_dynamics, you can use it as a probe to break any total torque into its three physical sources. The trick is to call it three times with different inputs and subtract:

  • $\mathbf{c}(\mathbf{q}) =$ five_dof_dynamics(q, 0, 0) — the gravity baseline.
  • $\mathbf{D}(\mathbf{q})\ddot{\mathbf{q}} =$ five_dof_dynamics(q, 0, qdd) - c(q) — pure inertial contribution.
  • $\mathbf{h}(\mathbf{q},\dot{\mathbf{q}}) =$ five_dof_dynamics(q, qd, 0) - c(q) — pure velocity-dependent contribution.

The sum equals the full torque (modulo numerical noise). This decomposition is invaluable for debugging control performance — if your tracking error correlates with one of these components, you know which compensation to add.

The function is a black box, but with three calls you can see every component working. That's how you debug controllers without opening the math.
Use this when. Tracking error spikes during fast motion → look at velocity component. Steady-state offset at a particular pose → look at gravity. Overshoot when accelerating → look at inertial.

Now you derive the component-decomposition trick yourself. Start from $\boldsymbol\tau = \mathbf{D}(\mathbf{q})\ddot{\mathbf{q}} + \mathbf{h}(\mathbf{q},\dot{\mathbf{q}}) + \mathbf{c}(\mathbf{q})$ and pick which inputs to zero out at each step — until you've isolated each term.

Component-by-component torque breakdown
function analyze_dynamic_components(q, qd, qdd)
    tau_total    = five_dof_dynamics(q, qd,        qdd,       'rad');
    tau_gravity  = five_dof_dynamics(q, zeros(5,1), zeros(5,1),'rad');
    tau_inertial = five_dof_dynamics(q, zeros(5,1), qdd,       'rad') - tau_gravity;
    tau_velocity = five_dof_dynamics(q, qd,        zeros(5,1), 'rad') - tau_gravity;

    fprintf('                J1     J2     J3     J4     J5\n');
    fprintf('Total:     %6.2f %6.2f %6.2f %6.2f %6.2f\n', tau_total);
    fprintf('Gravity:   %6.2f %6.2f %6.2f %6.2f %6.2f\n', tau_gravity);
    fprintf('Inertial:  %6.2f %6.2f %6.2f %6.2f %6.2f\n', tau_inertial);
    fprintf('Velocity:  %6.2f %6.2f %6.2f %6.2f %6.2f\n', tau_velocity);
end

9Three levels of control — what each layer of dynamics buys you

As your understanding of the dynamic terms grows, your controller can grow with it. Three progressive levels:

Level 1 — Pure PD. Ignores dynamics entirely. Works for slow, gravity-light motions. Will droop, will track sluggishly, but it's a baseline.

Level 2 — PD + gravity compensation. Adds $\mathbf{c}(\mathbf{q})$ as feedforward. Eliminates steady-state droop. The single highest-return upgrade in robot control.

Level 3 — Full inverse-dynamics feedforward. Computes $\mathbf{D}(\mathbf{q})\ddot{\mathbf{q}}_d + \mathbf{h}(\mathbf{q},\dot{\mathbf{q}}_d) + \mathbf{c}(\mathbf{q})$ along the desired trajectory and adds PD only for error correction. Required for fast trajectory tracking.

The progression is not optional — Level 2 must precede Level 3, because trying to feedforward the inertia term while ignoring gravity is asking for trouble.

Each level adds one term and earns one capability. Don't skip steps — every level you skip becomes a tuning headache later.
When each level is enough. Level 1: teaching demos, slow pick-and-place. Level 2: most industrial positioning. Level 3: high-speed trajectory tracking, contact tasks, anything where speed × precision matters.

Level 3 — full dynamic feedforward
function tau_full = full_dynamic_control(q_desired, qd_desired, qdd_desired, ...
                                         q_current, qd_current)
    tau_feedforward = five_dof_dynamics(q_current, qd_current, qdd_desired, 'rad');

    Kp = diag([50, 100, 80, 30, 20]);
    Kd = diag([5, 10, 8, 3, 2]);

    pos_error = q_desired - q_current;
    vel_error = qd_desired - qd_current;
    tau_feedback = Kp * pos_error + Kd * vel_error;

    tau_full = tau_feedforward + tau_feedback;
end

10What's slow about five_dof_dynamics.m, and why

The current implementation computes 125 Christoffel symbols by hand, line by line, and stores every $U$ matrix explicitly. It's correct, it's readable, and it's slow. Three structural problems:

  1. Computational redundancy. Every Christoffel symbol is a fresh trace(U*J*U') call — common subexpressions are recomputed dozens of times.
  2. Memory waste. All 15 first-order and 125 second-order $U$ matrices live in memory simultaneously, even though most are needed only briefly.
  3. Hardcoded geometry. The link lengths and masses are baked into the source. To run a different robot you'd have to rewrite the whole file.

The modern alternatives — recursive Newton-Euler ($O(n)$ instead of $O(n^4)$), symbolic preprocessing, GPU-accelerated batched evaluation — can buy you 10× to 100× speedups before you've changed any of the underlying physics. The Lagrangian formulation is pedagogically correct; the recursive formulation is what real-time controllers actually run.

The code you wrote is honest. It does exactly what the math says, in exactly that order. That makes it slow, but it makes it teach.
Newton-Euler vs Lagrangian. Same physics, different recursion. Newton-Euler is $O(n)$ per evaluation and is what real-time control loops run. Lagrangian is $O(n^4)$ but transparent — which is why we teach it first.
